**WHAT：** JSON 修复是当 LLM 输出结构损坏（混进解释文字、多了尾逗号、流式截断）时，把它救回可解析状态的工程手段。修复阶梯从便宜到贵：① 提取——用正则或 markdown 代码块定位 JSON 片段；② 容忍解析——允许尾逗号、单引号、注释的宽松解析；③ 截断补齐——流式被掐断时定位最后一个完整对象、补全括号；④ 模型修模型——把报错信息和坏 JSON 喂回 LLM 让它修，用低温参数。

**WHY：** 约束解码是事前预防，但生产上你总会遇到老模型、第三方 API、流式截断，格式故障无法归零。没有修复层，一次格式错误就直接任务失败，或者引发无脑重试风暴。面试被问"模型输出格式错了怎么办"，只答"重试"或"开 JSON mode"都太薄，修复阶梯才是有工程深度的答案。

**HOW：** 最小落地四步：包一层 parse_with_repair()，先严格 json.loads，失败逐级走阶梯，每步记录用了哪一级；修复成功后打 telemetry，统计哪一级救回来的样本最多，针对性上约束解码；修复仍失败的进死信队列或重试，别静默吞掉；攒历史坏样本做回归集，每次改 prompt 后跑一遍。

面试一句话：**预防靠约束解码，兜底靠 JSON 修复阶梯——生产 Agent 两层都要有。**

30 分钟小练习：写一个约 30 行的 parse_with_repair()，准备 3 个坏样本（带注释、尾逗号、流式截断），跑通阶梯并打印每个样本被哪一级救回。

预计用时：≤30分钟

完成判定：3 个坏样本能被救回为合法 JSON，脚本能报告每个样本走了修复阶梯的哪一级。
