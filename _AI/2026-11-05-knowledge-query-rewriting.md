**WHAT：** 查询改写是 RAG 检索前把用户原始问题改造成更利于检索的形式的环节。常见三招：① 多查询扩展——让 LLM 把一个问题改写成 3~5 个不同措辞的子查询，分别检索后合并去重；② HyDE（假设性文档嵌入）——先让 LLM 生成一段假想答案，再拿这段答案的向量去向量库检索，绕开 query 口语和文档书面语的风格差；③ 对话改写——多轮对话里把"那它呢？"这类省略指代补全成自包含问题。

**WHY：** 检索质量的上限由 query 决定。用户的问题往往短、口语化、带指代，和文档的 embedding 不在同一语义空间，直接检索召回率天然偏低。面试被问"RAG 效果不好怎么调"，第一层答案通常是先修查询改写——成本低、见效快，比换 embedding 模型和上图谱检索都排得更靠前。

**HOW：** 最小落地四步：把多轮对话历史连同当前问题一起送给 LLM，要求输出自包含改写版；复杂问题生成 3 个改写变体并行检索；走 HyDE 路线就先采样生成假想答案再做向量化；所有改写版本的召回结果合并去重后统一进 rerank 收口，重排始终放在最后一道。

面试一句话：**Embedding 模型决定检索下限，查询改写决定检索上限。**

30 分钟小练习：在你的 RAG demo 里加一个 rewrite 步骤——用 LLM 把用户问题改写成 3 个变体并行检索，对比改写前后 top-5 的命中率，写 5 条对比记录。

预计用时：≤30分钟

完成判定：3 个改写变体稳定生成，至少 2 条把正确文档召回到 top-5。
