## 今天要回答的工程问题

同一个知识库里，A 和 B 都有“退款说明”。如果 B 的文档相关度更高，A 提问时能不能先搜到 B，再让模型决定哪些内容可以引用？

风险在检索结果进入模型上下文的那一刻就已发生。即便最终回答没有展示机密，未经授权的数据也已流入不该接收它的组件。

今天把边界缩成一句话：

> 从可信认证上下文确定租户，在授权范围内筛选候选，再排序和截取 Top-K；身份缺失时直接拒绝。

这里的“租户”可以理解为互相隔离的组织或工作空间。用户输入和模型生成的工具参数，都没有权力自行决定可读哪一个租户。

## 可直接运行的最小实验

刻意把 B 的文档放在前面，并让它含有更多 `refund`。这样一旦漏掉权限条件，相关度排序就会把 B 的文档排在 A 前面，测试能明确暴露错误。

```python
DOCS = [
    {'id': 'B-1', 'tenant': 'B', 'text': 'refund refund B_ONLY'},
    {'id': 'A-1', 'tenant': 'A', 'text': 'refund A_ONLY'},
]


def retrieve(query, authenticated_tenant, model_args, k=1):
    if not authenticated_tenant:
        raise PermissionError('missing authenticated tenant')
    # 模拟服务端注入的认证上下文；不使用 model_args 中的 tenant。
    allowed = [d for d in DOCS if d['tenant'] == authenticated_tenant]
    ranked = sorted(allowed, key=lambda d: d['text'].count(query), reverse=True)
    return [d for d in ranked if query in d['text']][:k]


def run_tests():
    def ids(result):
        return [d['id'] for d in result]

    assert ids(retrieve('refund', 'A', {})) == ['A-1']
    assert ids(retrieve('refund', 'B', {})) == ['B-1']
    assert ids(retrieve('refund', 'A', {'tenant': 'B'})) == ['A-1']
    assert retrieve('refund', 'C', {}) == []
    try:
        retrieve('refund', None, {'tenant': 'B'})
    except PermissionError:
        pass
    else:
        raise AssertionError('missing authenticated tenant must be denied')
    print('5 cases passed')


if __name__ == '__main__':
    run_tests()
```

运行：

```bash
python3 retrieval_isolation_lab.py
```

`model_args` 在演示中被有意忽略，用来表达“模型提供的租户值不参与授权”。生产工具可以直接不暴露这个字段，或显式拒绝包含该字段的调用。真正的 `authenticated_tenant` 必须由服务端认证及成员关系校验得出；不能像练习一样接受调用者随意传入字符串。

### 五个用例各自证明什么

| 用例 | 预期 | 覆盖的边界 |
|---|---|---|
| A 查询 | 只返回 `A-1` | 正常访问不受另一租户排序影响 |
| B 查询 | 只返回 `B-1` | 隔离条件没有把所有请求都写死为 A |
| A 在模型参数里伪造 B | 仍返回 `A-1` | 工具参数不能覆盖认证身份 |
| C 没有文档 | 空列表 | 无授权结果时不回退到全库 |
| 没有认证身份 | 抛出拒绝异常 | 缺身份时失败关闭 |

第三个用例尤其适合面试讲解：自然语言请求可以提出“去查 B 的资料”，权限判断仍然由应用执行。

## 为什么筛选顺序值得单独说明

如果先在全库截取 Top-1，再过滤租户，B 的高分文档会先占满唯一名额；过滤后 A 得到空结果，即使它明明有自己的文档。这会同时带来检索质量问题和后续误用数据的风险。

本实验先筛授权候选，再排序。接入真实向量检索后，应核实数据库的过滤语义、近似检索行为及召回表现，不能仅凭参数名叫 `filter` 就假定安全和召回都已经满足要求。

还有一个重要边界：**五个用例只验证这个内存函数的约束。** 它没有验证登录系统、文档上传归属、细粒度访问控制、撤权同步、缓存隔离或日志访问。真实系统还需要确保可信文档元数据不被普通上传者篡改，所有检索路径都执行授权，在把内容交给模型前保留防御性检查。这些留待后续专题，今天不展开实现。

今天交付一个 `retrieval_isolation_lab.py`，满足以下条件就算完成：

